Vercel Cron cannot drive the route as written: cron issues `GET` (the route is POST-only) and sends `Bearer $CRON_SECRET`, not the drain secret. Documented in RB-09, deliberately not guessed at
- (Handoffs) **`DrainResult.parked` is `number | null` and `null` means the count FAILED, not that the backlog is empty.** Every consumer distinguishes them — the type, the script's three-branch printer, the route, and RB-09's table. Do not "simplify" it to `number`
- (Handoffs) **`fn_seed_system_actor()`'s two call sites are both load-bearing and neither is what creates the principal on a fresh database** — `trg_reconcile_system_actor` beats both on the seed's first `role_permission` INSERT. Someone tidying up will find two calls that appear to do nothing and delete one. The migration header explains why; keep it
- (Handoffs) `middleware.ts`'s `PUBLIC_PATHS` entry for `/api/outbox/drain` is the difference between the endpoint working and 307-ing to `/login`. It reads like a cosmetic list entry and is now pinned by a test. (That same list still contains `/api/health`, for which no route exists — pre-existing drift)
- (Handoffs) A handoff task is created **unassigned**, so it does not appear on the Tasks page's default `mine` tab; a Logistics user must switch to department or all. The department tab matches `task.department` against `app_user.department` as **free text** while the template hardcodes `'Logistics'` and `app_user.department` has no vocabulary — a differently-spelled department sees nothing
- (Handoffs) Smaller carried items: `claimRow` returning null is a *skip* not a *failure*, overloading "another drain holds it" with "the `created_by` join found nothing" (unreachable today, but it is the invisible-skip mode the migration argues against); `MAX_ATTEMPTS` is a global counter so overlapping drains can burn two attempts on one row in a wave; `recordFailure`'s guard stops the write being wrong but not from waiting behind a concurrent claim up to the 15s `statement_timeout`; an empty-string `task_template_key` parks after five attempts; `limit` is code-level only, so RB-09's "use a bigger limit" advice has no operator-facing control; the route sets no `maxDuration`, so a full 100-event batch can 504 with no `DrainResult`; `createTaskInTx` has no direct test, only coverage through the drain
